# Venture Launch OS — AI-Native Website & Agent Readiness Standard

AI-native readiness is a core launch dimension for every applicable website built or upgraded by Venture Launch OS / VLA.

## Default process

Use:

- `playbooks/AI_NATIVE_WEBSITE_OPTIMIZATION.md` — master SEO → AEO → Agent Technology process
- `playbooks/SEO_AEO_AI_VISIBILITY.md` — search, content authority, citation and measurement
- `playbooks/AI_AGENT_READINESS_WEBMCP.md` — browser-native agent actions
- `templates/AI_AGENT_READINESS_CHECKLIST.md` — production audit

## Seven layers

Every website should be evaluated across:

1. **Search foundation** — XML sitemap, robots, canonicals, indexability, internal linking, mobile/performance.
2. **Entity/semantic clarity** — truthful schema, explicit business identity, products/services, locations, mechanisms and policies.
3. **AEO/content authority** — direct answers, real buyer Q&A, comparisons, case studies, original expertise/data and citation-worthy resources.
4. **Agent discovery** — optional compatibility assets such as llms files, structured catalogs, AI sitemap, agent manifests and machine-readable documentation.
5. **API/CLI/MCP** — deterministic service interfaces, OpenAPI, safe CLI documentation and server MCP when real business operations justify them.
6. **WebMCP** — safe browser-native agent tools for valuable user journeys where current support and ROI justify implementation.
7. **Measurement** — search performance, generative-search visibility/citations, agent-tool usage, qualified leads, customers and revenue.

## VLA behavior

For a new venture, VLA should design these layers into the architecture from the start, without delaying first revenue for low-value experimental technology.

For an existing website, VLA should run the AI-Native Website Optimization audit, score all applicable layers, prioritize by economic value, fix foundational search/entity problems first, then implement machine-readable and agent-operable capabilities.

## Important distinctions

- SEO is foundational to generative search visibility.
- AEO/GEO should improve usefulness, grounding and citation-worthiness, not create commodity content at scale.
- `llms.txt`, AI sitemaps and CLI documentation are compatibility assets for systems that use them; they are not guaranteed Google ranking factors.
- OpenAPI describes real APIs.
- MCP exposes approved server/service tools to compatible agent clients.
- WebMCP exposes approved webpage/browser-context tools to compatible browser agents.
- An XML sitemap remains the canonical search discovery sitemap; an AI-oriented catalog/sitemap is supplemental.

## Truth and security

Never create fictional endpoints, capabilities, pricing, availability, reviews, partners, certifications, customer proof or completed transactions to make a site appear more agent-ready.

Agent actions must respect the same authentication, authorization, confirmation, legal/financial, payment and privacy boundaries as the human workflow.

## Source tracking

For WebMCP, follow the current Web Machine Learning Community Group specification rather than historical community syntax.

For MCP, follow the current official Model Context Protocol specification and SDK guidance rather than stale protocol assumptions.

These technologies are evolving; VLA must verify current syntax/support at implementation time.

## Completion rule

Do not call a website AI-native or agent-ready because it has schema, an `llms.txt` file, or an MCP-looking endpoint.

The applicable layers must be truthful, production-tested and measurable.

The economic goal is greater qualified discovery, easier human/agent interaction, lower conversion friction and measurable business outcomes.
